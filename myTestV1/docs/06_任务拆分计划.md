# 06 任务拆分计划

## 1. 规则

- 一个任务 = Claude Code 一次会话内可完成的工作量。
- 任务按依赖顺序执行；前置任务未 `DONE` 不得开始。
- 每个任务的「产出」是该任务唯一允许修改的范围（`docs/PROGRESS.md` 除外）。
- 「全量检查点」任务的冒烟命令包含 `dotnet test ScreenFlow.sln -c Release`（全部测试）。

## 3. 反馈任务（FB-xx）模板

用户把本机验收结果放到 `feedback/<时间戳>/` 后，在 PROGRESS 追加 `FB-xx`。执行方式：

1. 读 `feedback/<时间戳>/summary.md` 与 `summary.json`，逐个失败项分析原因。
2. 原因属于“实现缺陷” → 修复并在夹具中**补充能复现该缺陷的最小形态**与测试（测试名前缀 `Fb<xx>_`）。
3. 原因属于“事实手册未覆盖的源码形态” → 在 `config/unitypos.json` 中扩展（若是配置能解决的），或在夹具中补充该形态并扩展适配器；在 PROGRESS 的「待本机确认」中记录新的确认点。
4. `confirmations.md` 中用户给出的确认结论 → 更新 `config/unitypos.json`，并删除 PROGRESS 中对应的「待本机确认」行。
5. 冒烟：全量 `dotnet test` + `python -m pytest python/tests -q`。
